## Глава 1. Информационные системы

### Подход курса
- Курс сугубо практический, идеи намеренно упрощаются. Строгие формулировки — в материалах ISTQB.
- Обозначения в материалах: **Q:** — вопрос, **A:** — ответ.

### Что такое тестирование
- Тестирование ИС = проверка, что функции системы работают правильно (перевод денег со счёта на счёт, пополнение баланса и т.д.).

### Информационная система (ИС)
- **ИС = программы + оборудование + сотрудники** (иногда добавляют пользователей).
  - Программы — выполняют функции.
  - Оборудование — смартфоны, компьютеры, серверы, на которых программы работают.
  - Сотрудники — отвечают за работу программ и оборудования (от гендиректора до программистов и юристов).
- **Зачем нужны ИС:** облегчать жизнь, решать задачи пользователей.
- Модель «сервис»: **компания создаёт ИС → пользователи используют ИС для получения сервиса (услуги)**. ИС должна решать задачу пользователя: купить, оплатить, отправить, получить, посмотреть.
  - Alif Bank предоставляет банковский сервис через ИС **Alif Mobi** и **Алиф Онлайн**.
  - Telegram — сервис обмена сообщениями; Google/YouTube — видео-сервис. И так почти для всего.

### Кто создаёт ИС (команда)
1. Аналитики — продумывают, что сделать.
2. Программисты — пишут код.
3. Тестировщики — тестируют код программистов.
4. Администраторы / DevOps — непрерывная работа кода.
5. Менеджеры проектов — координируют всех.

### Типовое устройство ИС
1. **Клиентское приложение** — с ним взаимодействует пользователь.
2. **Серверное приложение** — принимает запросы от клиента.
3. **База данных** — хранит данные.
- Связь клиент ↔ сервер — через **Интернет**.
- Пользователь — на своём устройстве (смартфон/компьютер); сервер и БД — на оборудовании компании.

### Двусмысленность слова «сервер»
- «Сервер» = либо компьютер (железо), либо серверное (приложение). Каждый раз уточнять по контексту.

### Почему не одно приложение, а набор
- Ключевая задача компаний — быстрее выпускать обновления. Ускорение только за счёт разделения работы:
  - backend — серверное приложение;
  - mobile — мобильные приложения;
  - frontend — пользовательская (веб) часть.
- Под каждое направление свой стек технологий, один человек всё знать не может.

### Сленг (обязательно знать)
- В живом общении: **«бекэнд» / «сервак»** вместо «серверное приложение».
- Термины даются в английском написании: **backend, frontend, mobile**.

### Клиентское приложение
- То, с чем взаимодействует пользователь. Назначение — понятный интерфейс (кнопки, поля ввода), чтобы пользователь решал свои задачи.
- Три популярных варианта (на примере Telegram):
  1. **Desktop** — программа на компьютере (Telegram Desktop).
  2. **Frontend / Web** — приложение в браузере (Telegram Web).
  3. **Mobile** — приложение на смартфоне (Telegram).
- При действиях в интерфейсе клиент **отправляет запросы (сообщения) на сервер** (например, совершение платежа). Для большинства задач нужен Интернет.

### Серверное приложение (backend)
1. **Безопасность:**
   - доступ только к **своим** данным;
   - доступ к своим данным **с разных устройств** (мобильное приложение, браузер и т.д.).
2. **Бизнес-логика** (сложная логика): общие правила работы системы — расчёт комиссий, начисление процентов по вкладам и т.д. Она общая для всех клиентов, поэтому живёт на сервере, а не на каждом клиенте (и по безопасности тоже).
- В отличие от клиентов (вкл/выкл когда угодно), **сервер работает постоянно (24/7)**. **Один сервер обслуживает много клиентов.**

### База данных
- Правильно — **СУБД** (Система Управления Базами Данных), обычно говорят просто «БД». Специальное приложение для **надёжного хранения данных**.
- Хорошую БД писать десятки лет, поэтому компании пишут только клиент + сервер, а БД берут готовую:
  - Бесплатные: **PostgreSQL, MySQL/MariaDB**.
  - Платные: **Oracle, Microsoft SQL Server**.

### Детали про Alif (запомнить!)
- **Alif Mobi** — мобильное приложение банковских услуг: баланс счёта (на скриншоте 2 904,64 с. + 234,8 бонусов), QR-платёж, снятие наличных, услуги Алифа, переводы («Из за рубежа в Таджикистан», «Переводы за рубеж»).
- Архитектура Alif Mobi со слайда: смартфон (Android, alif mobi) → Интернет → **сервер на Go** → **БД PostgreSQL** (слон).
- **Алиф Онлайн** — веб-версия банковского сервиса Alif Bank.
- **Эмулятор Alif Bugs Company**: онлайн `https://alif-bugs.pro`, локально `http://localhost:8000`. Раздел: **«Информационные Системы → Схема работы типовой ИС»**. Демо: перевод средств (получатель `**** 1234`, сумма 100, кнопка «Отправить», «Лимит на переводы») → цепочка `HTTP Request → Backend → SQL Query → Database`.
- Визуальное представление работы системы критично: без него нельзя предположить, где что сломается. **В тестах будут вопросы по демонстрациям эмулятора.**

### Модель «запрос-ответ»
- Приложения ИС обмениваются сообщениями, как в чате:
  - **Запрос (request)** — одно приложение просит другое выполнить операцию.
  - **Ответ (response)** — результат выполнения (успешно / не успешно).
- Названия зависят от пары приложений:
  - Клиент ↔ сервер: **HTTP**, сообщения — **HTTP Request / HTTP Response**.
  - Сервер ↔ БД: **SQL**, сообщения — **SQL Query** (Request) / **SQL Response**.
- Пока запомнить только названия, детали — в следующих лекциях.

### Эталонная цепочка (кнопка «Отправить» в эмуляторе)
1. Клик «Отправить» в клиенте → создаётся **HTTP Request**.
2. HTTP Request уходит на **backend**.
3. Backend формирует **SQL Query** в БД.
4. БД возвращает **SQL Response** backend'у.
5. Backend формирует **HTTP Response** клиенту.
6. **Frontend** показывает интерфейс по ответу backend'а.

## Глава 2. Тестирование: процесс и правила

### Определение
- **Тестирование (упрощённо) = проверка, что фактическое поведение системы соответствует ожидаемому.**

### Шаг 0 — изучение системы
- Сначала изучаем систему и выделяем **основную функцию** (калькулятор: «считать» — складывать, умножать, делить; знаем из предыдущего опыта).
- Если система новая (пример: форма с App name / Container image / pods / service) — разбираться по каждому элементу: что за название, образ, поды, сервис.

### Откуда брать информацию о системе
- **Профессиональные** системы/пользователи — есть **документация** (что и как работает).
- **Обычные** — документации почти нет; вместо неё: интуитивный пошаговый интерфейс, обучение, FAQ (пример — FAQ Telegram), пошаговые материалы, короткие видео (Telegram/YouTube).
- Даже у профессиональных: документации может **не быть / неполная / устаревшая / с ошибками**. Это нормально.
- Три источника (ключевое):
  1. **Предыдущий опыт** (калькулятор).
  2. **Самостоятельное изучение** (Alif Mobi: сайт → описание → поставить на смартфон → пользоваться).
  3. **Общение с командой** (техподдержка Alif, вопросы, экскурсия в Alif — отработаем в конце курса в командах; пока только 1–2).
- Чаще дают описание **конкретных функций**, а не всей системы → умеем работать при: ограниченном объёме инфо, необходимости задавать вопросы, необходимости самоанализа.

### Типовой процесс тестирования
0. Изучение системы.
1. **Подготовка данных** (= **тестовые данные**): пример (2 + 2) + ожидаемый результат (4).
2. **Вызов функции** (ввод + `=`).
3. **Сравнение** ожидаемого с фактическим.
- Калькулятор: совпало → хорошо; не совпало → **ошибка в программе ИЛИ в наших вычислениях «в уме»**.
- Правило: **ожидаемый результат всегда перепроверяем сначала** (дальше считаем это само собой разумеющимся и не пишем).

### Баг
- **Баг (bug)**: факт ≠ ожид **+ мы уверены, что сами в ожидаемом не ошиблись**.
- Совпало → «система при данной проверке отработала корректно».
- В IT — англоязычные термины и их кальки (рус/тадж).

### Образ мышления
- Входные + ожидаемый → действие → сравнить мысленно. Тренировать в обычной жизни — будешь находить больше ошибок автоматом.

### Неявные («дополнительные») шаги
- Изучили систему; подготовили приложение (запустили); подготовили данные; на каждом шаге неявно проверяли (пример вводится в окошко, кнопки жмутся, результат выводится); сравнили.
- **Важно: любое действие, где верное ожидаемое ≠ фактическому = баг.** В лекциях доп. шаги пишут только при необходимости.

### Три причины ошибок (стартовый набор)
1. **Действия пользователя** (просят Email — вводит телефон).
2. **Среда функционирования** (сломался сервер, отключили свет).
3. **Ошибки разработчиков** (неверная формула проверки/расчёта процента).

### Зачем проверяем (принятие решений)
- Чтобы дать информацию для решения: **может ли система обслуживать клиентов**.
- Аналогия с водителем: **критичные** (отвалилось колесо — ехать нельзя) vs **некритичные** (сломан плеер — ехать можно). **Не все ошибки одинаково критичны!**
- Проверяем мы (тестировщики), решает команда / руководитель проекта.

### Практика по скриншоту (форма «Обратная связь»)
- Определить основную функцию по скриншоту → тест: данные + как вызвать + как сравнить → **записать НА БУМАГЕ** (не «в уме»). Формулировать на бумаге — с самого начала.
- Идея лекции: **не жди идеального момента**, пользуйся знаниями, которые уже есть.

### Золотое правило (спасает от проблем)
- **НИКОГДА не тестируем системы без разрешения владельца!** Можно случайно сломать → ответственность от административной до уголовной (критические/государственные системы).
- Нельзя вводить чужие email/телефоны — это данные реальных людей.
- Разрешено: **только эмулятор** (локально / alif-bugs.pro). Email для лекции: `*-tester@alif-bugs.pro`, `student@alif-bugs.pro`.
- Время обычно согласуется (пример: 1–14 марта, 09:00–14:00, Душанбе); дальше считаем, что разрешение = согласованное время. **Эмулятор — в любое время весь курс.**

### «Работает корректно» и ограничения
- Frontend показал «Ваше сообщение успешно отправлено!» ≠ всё корректно: **видим только клиент (1), сервер и БД (2, 3) не видим**.
- Доступа к серверу/БД не дадут (не сотрудник, безопасность). Выход: **проверяй то, что есть (frontend), проактивно, не жди идеальных условий!**
- Формула: «работает корректно» + **«в рамках ограничений проверок»**. Отсутствие доступа = ограничения.

### Формы эмулятора «Тестирование → Обратная связь» (раздел 2-й лекции)
- **normal** — эталон: при правильном заполнении работает корректно. Сравнивать: хватает ли данных; совпало ли поведение (вызов + результат); корректно ли.
- **error** (ошибка среды): «Ошибка отправки сообщения! Попробуйте повторить запрос позже». Запомнить: разработчики **специально** предусматривают оповещение, чтобы пользователь: 1) понял, что ошибка, 2) получил указания, что делать дальше. «Попробуйте позже» — не идеал, но лучше, чем ничего. Ошибка ≠ всегда вина разработчика (мог сломаться комп с backend); **нет инфы, что временная → сообщаем как баг**.
- **buggy** (ошибка разработчика): неверный Email → красная подсветка = правильно (исправляй и дальше). Но **правильный Email (`student@alif-bugs.pro`) тоже подсвечен красным = баг**, сообщаем разработчикам. Разработчики ошибаются часто — быть готовым. Главный вопрос: **в какой момент ожидаемое не совпало с фактическим?**
- **slow** (время): время — «скрытый» параметр, его часто не озвучивают. Засечь секундомером: когда появляется подозрение «зависло» и желание покликать/обновить. Нормы: простые функции — **1–2 сек** (при хорошем интернете; большие файлы — дольше); форма обратной связи — **максимум 10 секунд** (ответ разработчиков); переводы Alif — «в течение нескольких минут». Процесс: изучить → собрать вопросы → уточнить у разрабов → тестировать → повтор.
- **unknown** (непонятное): ни успеха, ни ошибки. Нужны пояснения разрабов: что при успехе / неуспехе / неверном вводе (поле красным). После получения инфы — уверенно баг.

### Типовые сценарии (итог лекции)
1. Общая ошибка (неясно: временная или программиста). 2. Ошибка программиста. 3. Долгие операции. 4. Непонятное поведение.
- Проверяем глазами обычного пользователя; инфы всегда недостаточно → **собираем ВСЕ вопросы списком, потом идём к разработчикам** (не бегаем с каждым по одному).

### Чеклист тестирования
1. Изучить систему: задача; функции; пользователи; устройство; аналоги.
2. Разрешение на функцию конкретными типами. Не указаны — согласовать: позитивное + негативное функциональное black-box. Что и как — решает заказчик.
3. Сформировать классы эквивалентности и границы для данных.
4. Получить данные, запросить недостающие по классам, согласовать.
5. Проверить функцию по типам: a) валидные; b) невалидные; c) скорость; d) визуальный отклик.

## Глава 3. Типы тестирования

### Зачем типы
- Типы = группы «что» и «как» тестируем. Зная их, сразу понимаешь задачу. Пример: «позитивное функциональное тестирование перевода с карты на карту методом чёрного ящика».
- Со временем будешь специализироваться на типах и приложениях (локализация — языки, безопасность — уязвимости).

### Учебный пример: перевод с карты на карту (аналог AlifPay)
- Эмулятор: «Типы тестирования → Перевод с карты на карту». Функция одна — перевести сумму.
- Данные: отправитель `4242424242424242`, срок в будущем (`09/30`), CVC любой (`111`), код `9999`; получатель `5555555555554444`. Аккуратно ввёл → «Ваш перевод успешно отправлен!». Но всё ли хорошо?
- Что замечаем (предыдущий опыт): подписи залезают на поля (UI); на маленьком экране форма «ломается»; на английском переведено не всё («Номер карты» осталось); у кодов подтверждения обычно лимит времени (59 секунд) и кнопка «Отправить код повторно».
- Наблюдай за приложениями, которыми пользуешься (мессенджеры, игры) — так копится опыт для сравнений.

### Опасные эксперименты (раздел dangerous)
- Чужие данные в реале — только с письменного разрешения. «Повезло» и угадал чужую карту → списал деньги → владелец в банк → банк ищет «мошенника» вплоть до милиции. Так часто попадают новички.
- Угадал только номер: жалобы из-за СМС-кодов, блокировка карты за подозрительную активность.
- Правило: явное разрешение + списки допустимых данных (карты, телефоны, ФИО). Даже «придуманное» может оказаться реальным.

### Неверные данные (тоже нужны — система должна отвечать ошибкой)
- Заведомо неверный номер; заблокированные; недостаточный баланс; истёкший срок. Тоже запрашивать и согласовывать сразу.
- Заведомо неверный = два момента:
  1. Номера строятся по правилам — **Алгоритм Луна**: не следующий ему номер точно ничей.
  2. Система поддерживает не все карты — **Alif Pay только Корти Милли** (Visa/MasterCard — нет).
- Проверка: `Card Number Validator Online` (реальные номера не вбивать!), генераторы: `Card Number Generator Online`. Для других данных валидаторы тоже есть, но под США/Европу/Россию — под Таджикистан нет: писать самим или просить у команды.
- Нужной системы в списке может не быть (нет Корти Милли и Мир). Даже неверные данные согласовывать — иначе СБ решит, что ты хакер.
- Практика: раздел invalid — подобрать 16 цифр не по Луну → «Опечатка в номере карты».
- В документации описывают работу с корректными данными; про неверные — молчок или частично.

### Шесть разрезов (упрощённо, остальное — ISTQB)
1. **По объекту.** Функциональное (функции: ожид vs факт). Нефункциональное: UI (аккуратность, наезды, видимость), Usability (удобство), Локализация (полнота перевода), Безопасность (уязвимости). Сначала функциональное, потом остальное. Исключение: переводы уже есть в таблицах, а система не готова — проверяем сразу («Номер карты» → «-» = нет перевода). Заметил чужое при функциональном — доп. списком (Функциональные баги / Другие баги). Просили НЕ тестировать перевод — замеченное не передаёшь.
2. **По запуску.** Статическое (доки, переводы, код — не запускаем). Динамическое (запускаем). «Протестируйте систему» = обычно динамическое.
3. **По позитивности.** Позитивное (верные данные → верный ответ). Негативное (неверные → корректная обработка: сообщения, указания на опечатки). Обычно сразу оба. Все данные согласовывать.
4. **По знанию устройства.** Чёрный ящик (только интерфейс, внутри не видим). Белый (знаем всё, лезем везде, смотрим БД). Серый (частично). Внутри компании — обычно белый; снаружи — любой. В начале курса — black-box.
5. **По автоматизации.** Ручное (руками + сравниваем). Автоматизированное (программа жмёт и сравнивает). С элементами автоматизации (программы-помощники). По умолчанию — ручное/с элементами; автоматизированное указывают явно.
6. **По функциям** (обновления: новое, улучшение старого, фикс ошибок). Новых функций. Регрессионное (старое не сломалось в новой версии). Повторное (баги исправлены).

## Глава 4. Тестовые данные

### Какие данные запрашивать
- В реале данные связаны с миром: SMS на телефон, списание с карты, письмо на email. Что брать — запрашивать у заказчика/владельца.
- У ползунка кешбэка («Тестовые данные → Карта с кешбэком (range)», black-box): min 0, max 200 000, default 0.
- Всегда запрашивай: min, max, default (первые три выяснишь и сам) + **самые частые значения (не среднее!)**. Частые могут не знать или не раскрыть (банк молчит о расходах).
- Пример: загрузки как у YouTube — 70% файлы 10–50 Мб, 20% 300–500 Мб → тестируем в первую очередь их. Среднее (100 Мб) ни к чему не относится — от средних отказываемся.
- Удобство детально не тестируем — только фиксируем совсем неудобное (нет единиц, нет подписей, ползунком точную сумму не ввести) и отдаём предложения команде.

### Классы эквивалентности
- Не знаем внутренностей → делим значения на классы, где любое = любому (тот же алгоритм). Частые значения — отдельным классом. Из каждого класса — одно случайное значение.
- Пример: классы [min–1000], [1000–8000], [8000–max] → проверяем 500, 1774, … — вместо 200 000 всего 3 проверки. Всё проверить невозможно — упрощаем общепринятыми подходами.
- Проверка: 1774 × 0,03 = 53,22 → в приложении 53,22 → PASS. Начинаем с самых частых.
- Классы смотрят и со стороны результата: класс 1 → 3%, класс 2 → всегда 3000с (максимум). Граница: 3000 / 0,03 = **100 000**. Итого 4 класса вместо 200 000. Другие подходы — нормально; делай как полезно проекту.

### Граничные значения
- Ошибки чаще на границе и рядом. «От 1000с бонус 10с» — это 1001+ или 1000+? Уточнить у разрабов.
- Проверяем границу + влево/вправо: 99999 / 100000 / 100001. За min/max выйти нельзя, края выпадают.
- Итого: 4 значения классов + 13 граничных = **17 вместо 200 000**.

### Поле ввода вместо ползунка (раздел input)
- Новые классы: больше 200 000; отрицательные; вещественные (1000.99999); пробелы (10 000); текст. Часть — в негативные, часть может быть позитивом (1000.99, 10 000 — если разраб не запретил). Приоритет уточнить у заказчика; важнее — правильный формат.
- Ползунок не убирают: кому-то удобнее точное число, кому-то ползунок (раздел combined).

### Комбинаторика (два поля: «Тестовые данные → Депозит»)
- Классы + границы по каждому полю → комбинации. Позитив: срок до 3 (10%), 3–6 (11%), 6–9 (12%), 9–12 (13%), 12+ (14%); свыше 50 000 +1%.
- Срок: 5 классов, 17 значений (границы 0, 3, 6, 9, 12, 18; около 1, 2, 4, 5, 7, 8, 10, 11, 13, 17; внутри 15). Сумма: 2 класса, 9 значений (0, 1; 49999, 50000, 50001; 152399; 199999, 200000). 17 × 9 = **153** — много.
- Выход: популярные сроки 3–6 и 6–9 (8 значений) × 9 сумм = **72**; остальным срокам — хотя бы по одному значению. Вывод: чем больше параметров, тем больше проверок.

### Нечисловые классы (поверхность, варианты копи в работе)
- Карты: 16 цифр — валидные по Луну (Visa, MC, МИР, Корти Милли) / невалидные; не 16 цифр; пробелы; опечатки.
- Телефоны: страны и операторы; форматы (+992 / без); дефисы, пробелы, скобки; неверный код страны; опечатки.
- Имена: алфавиты (ғ, қ); спецсимволы (О'Коннор, Анна-Мария); короткие (1–2); длинные (60+); цифры.

### Итог главы
- Времени мало → проверяем самое важное (частое) + как можно больше: классы + границы + частые значения у заказчика. Опора на эти подходы — показатель уровня.

## Глава 5. Процесс тестирования и документы

### Процесс (6 шагов)
1. Заказчик ставит задачу: что и как тестировать.
2. Тестировщики составляют план и утверждают с заказчиком.
3. Придумывают и проводят тесты.
4. Оформляют баг-репорты.
5. Разработчики исправляют (если успевают) → тестировщики перепроверяют.
6. Отчёт о тестировании.

### Процесс в курсе
1. Команда 3–7 человек, лидер + заместитель (на каждый проект — новые). Закрытый чат в Telegram с оргами.
2. Лидер и зам встречаются с заказчиком: цели, задачи, сроки.
3. План → утверждение.
4. Тесты → проведение.
5. Баг-репорты.
6. Отчёт.
- Зачем команды: заказчик не будет говорить с каждым; учимся работать в команде. Собрать можно самому, но только из участников курса.

### Вопросы на встречу (систему смотрим, не трогаем)
- Что за система, зачем. Какие данные нужны для позитива/негатива (дальше первого экрана не пройти). Как проверим результат: сообщение «Ваша заявка принята», звонок, забрать карту. Всё записывает лидер.

### Встреча с заказчиком (только лидер + зам)
- Что ждут: функциональное? локализация? Документация (если дадут) или что за система, функции, как работают. Данные для тестов (телефоны, карты — или свои, на них откроют доступ). Сроки и время (напр. 1–14 марта, Пн–Пт 09:00–14:00, Душанбе). Контакты: вопросы + «мы что-то сломали».
- Всё — в документ **01. Информация о проекте**, публикуется в общем чате. Проверяют организаторы.

### План тестирования (документ 02)
- Что и как (типы). Данные: заказчика или свои. Даты и время. Состав (ФИО, телефоны). Контакты заказчика: вопросы / проблемы.
- Зачем: фиксирует встречу + после согласования = **разрешение тестировать**.

### Набор тестов (Test Suite)
- Каждый пишет краткий список: «заказ карты впервые на русском», «повторно на тот же номер», «с неверным телефоном». **Без приватных данных в названиях!** Где удобно: бумага, Telegram, Google Docs.
- Собрать: убрать дубли, обсудить, добавить. Оформление: чек-лист (первый проект) или тест-кейс (позже).
- Чек-лист = список дел, вычёркиваем сделанное. С доп. инфо: «Набор данных №1, ввод через поля».
- Наборы данных: приватное (логины, карты, CVC) не пишем — только внутри команды на бумаге, нумеруем (№1, №2), у каждого копия. Чей-то телефон в наборе → он берёт свой набор (иначе SMS не придёт). В компаниях могут разрешать корп. системы — уточнять правила.
- Распределить: успеть за 3–4 дня + 1 день на оформление багов. Тест → набор → ФИО. Лидер оформляет по **03. Набор тестов** и шлёт оргам.

### Проведение
- Запись экрана на каждый тест (отдельное видео). Только разрешённое время. Только согласованное. Отмечать выполненное.
- Запись нужна: убедиться, что сами не ошиблись; баг-репорт; доказательства. Инструмент любой, но не снимать экран на телефон; стандарт — OBS Studio (Win/Linux/Mac), разобраться самим.
- Нашёл баг: не спешить → пересмотреть видео → воспроизвести повторно с записью → не воспроизводится → пометка. Только потом репорт. Невоспроизводимые — **«плавающие»**.

### Баг-репорт (документ 04)
1. Номер (уникальный). 2. Краткое описание («Неверный кешбэк свыше 1000с»). 3. Дата/время создания с поясом (Душанбе). 4. Дата обновления (при повторе). 5. Название теста из 03. 6. Шаги + на каком шаге ожид ≠ факт. 7. Ссылка на видео (корп. проекты — не на публичные сервисы!). 8. Воспроизводимость. 9. Окружение (ОС + браузер). 10. Статус: Новый / Передан заказчику / Дубликат / Отклонён / Ожидает уточнений / Ожидает исправления / Ожидает проверки / Повторно открыт / Закрыт.

### Повторное тестирование
- Ответы: принято / нужны уточнения / отклонено. Дождаться фикса → перепроверить. Не исправлено → обновить репорт + новое видео → отправить снова.

### Отчёт (документ 05)
- Время, найдено, исправлено, не исправлено. По завершении — организаторам.
- Документы пока в файлах, позже — система. В компаниях форматы отличаются, но суть та же.

## Глава 8. Баг-репорты: как писать, чтобы чинили

Поля 04 — в главе 5. Здесь — правила хорошего репорта (86% коллег мучаются с чужими репортами, топ-3 важного: шаги, ожид ≠ факт, описание).

### Заголовок: что + где + когда
Плохо: «Не работает», «Ошибка», «Кнопка не работает».
Хорошо: «[Перевод] После кода 9999 нет сообщения об успехе», «[Кешбэк] Неверный кешбэк свыше 100 000».
Без «СРОЧНО» в заголовке и без решения вместо симптома.

### Шаги: только конкретика
Каждый шаг — литералы: какие данные (`4242424242424242`, `student@alif-bugs.pro`), куда нажали. Никаких «введите необходимое». Лишние шаги убрать (минимум для повтора). Указать номер шага, где ожид ≠ факт.

### Ожидаемое — из требований
«Должно работать корректно» — не ожидаемое. Источник: текст с сайта/макет («Ваш перевод успешно отправлен!»). Требований нет — пишем ориентир: «как в форме normal».

### Severity ≠ Priority
Severity — влияние, ставит тестировщик: блокер (падение/потеря данных) → крит (сценарий сломан) → major (функция сломана, обход есть) → minor (косметика). Priority — скорость исправления, согласует лид/заказчик. Не ставить всё высоким.

### Остальное коротко
- Один баг — один репорт. Перед отправкой — поиск дублей.
- Воспроизводимость: всегда / N из M / плавающий.
- Текст ошибки — текстом, не только скриншотом. Видео — как обычно.
- Тон нейтральный: факты без оценок и обвинений.
- Чек-лист: повторил 2–3 раза → шаги идут по тексту → расходящийся шаг указан → видео есть → приватных данных нет (только «набор №»).
